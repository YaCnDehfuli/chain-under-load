# Findings

What 81 Sigma rules for LSASS credential dumping do when they meet seven real
dumping tools, and what the misses have in common.

Every number here comes from `benchmark/results.json`, regenerated by
`python -m eval.report --run`. Method is in [docs/method.md](docs/method.md).

## What was measured

Seven captures from OTRF/Security-Datasets, each one recording of the same
technique carried out with a different tool, on the same lab host with the same
Sysmon configuration. 354,229 events in total.

| tool | events | what it is |
|---|---|---|
| logonpasswords | 53,698 | mimikatz-style in-process read |
| procdump | 42,482 | signed Sysinternals binary |
| comsvcs | 41,954 | rundll32 calling the comsvcs MiniDump export |
| out-minidump | 40,568 | PowerShell reflective MiniDumpWriteDump |
| sharpdump | 59,707 | .NET port of out-minidump |
| outflank-dumpert | 58,096 | direct syscalls, avoids userland hooks |
| nanodump | 57,724 | syscalls plus a hand-rolled minidump writer |

80 published rules select for T1003.001, 79 by ATT&CK tag and 1 by logsource.
Three rules from this repo carry the same tag, making 83 in the run. No rule
failed to compile.

## Coverage per tool

| tool | published rules firing | including this repo |
|---|---|---|
| out-minidump | 8 | 10 |
| procdump | 7 | 8 |
| comsvcs | 6 | 8 |
| outflank-dumpert | 5 | 6 |
| logonpasswords | 3 | 4 |
| sharpdump | 3 | 4 |
| nanodump | 3 | 4 |

Each tool trips between 3 and 8 published rules, median 5. 18 of the 80 fire on
at least one tool. The other 62 target tooling this corpus does not contain,
which is why the report leans on per-tool coverage rather than a per-rule score.
Of the 581 rule and capture pairs, 44 detected, 207 were logic misses, 273 out
of scope, and 57 were telemetry gaps.

No published rule detects more than 4 of the 7.

## The misses have a shape

### All three nanodump detections are one string

nanodump's three published detections each key on the literal `dump` appearing
somewhere the operator chose:

| rule | what it matched |
|---|---|
| LSASS Memory Access by Tool With Dump Keyword In Name | `SourceImage` was `nanodump.x64.exe` |
| LSASS Process Memory Dump Files | `TargetFilename` was `lsass_dump.dmp` |
| LSASS Dump Keyword In CommandLine | the same filename on the command line |

Rename the binary and the output file and all three stop firing, which takes
nanodump's published coverage to zero. sharpdump is in a similar position, with
two of its three published detections needing `dump` in the image name.

The behaviour underneath is still there. nanodump opened LSASS with
`GrantedAccess` `0x1010`, and `0x1010` is commented out of the two main
access-mask rules:

```yaml
# from proc_access_win_lsass_memdump.yml
GrantedAccess|contains:
    - '0x1038'
    - '0x1438'
    - '0x143a'
    - '0x1fffff' # Too many false positives
    # - '0x01000'  # Too many false positives
    # - '0x1010'   # Too many false positives
    # - '0x1400'  # Too many false positives
    # - '0x1410' # Too many false positives
```

That is a deliberate trade by the rule authors, not an oversight. It is worth
knowing that the trade costs nanodump and the in-process mimikatz read, both of
which use the masks that were removed.

### A directory filter that the tools walk straight through

`Potentially Suspicious GrantedAccess Flags On LSASS` drops every event whose
source lives in an ordinary program directory:

```yaml
filter_main_generic:
    SourceImage|contains:
        - ':\Program Files (x86)\'
        - ':\Program Files\'
        - ':\Windows\System32\'
        - ':\Windows\SysWOW64\'
```

In these captures procdump ran from `C:\Program Files\procdump64.exe`, SharpDump
from `C:\Program Files\SharpDump.exe`, and nanodump from
`C:\Windows\System32\nanodump.x64.exe`. The filter is there to suppress the
system processes that read LSASS constantly, and it does that. It also means
writing to a directory an operator can usually write to is enough to leave the
rule's field of view.

### Where the telemetry ran out

57 of the misses are the capture, not the rule. Most are rules reading a
channel this Sysmon configuration did not record, and they are reported
separately for that reason.

One of these bit me while writing my own rules. These captures carry process
creation on both Sysmon EventID 1 and Security 4688, but the flattened 4688
events expose the command line as `CommandLine`, not the `ProcessCommandLine`
that a 4688 rule would normally name. My first comsvcs rule used the documented
field, detected 0 of 7, and looked like a logic problem until the field
inventory said otherwise. Rewritten against `process_creation`, it detects the
capture it was written for. That is the exact failure mode `miss-telemetry`
exists to catch, and it is a good argument for classifying misses rather than
counting them.

## My rule

`rules/t1003_001_lsass_handle.yml` detects 7 of 7, with 8 false positives in
514,202 benign events, a rate of 1.56 per 100k.

It keys on the caller rather than on names the operator picks. Filters pin a
binary to its expected directory instead of excluding directories wholesale,
which is the gap nanodump used by running from System32 under its own name.

The 8 false positives, in full:

| source | count | note |
|---|---|---|
| Azure `CollectGuestLogs.exe` | 6 | guest agent, six build-specific paths |
| `powershell.exe` | 2 | one 0x1010, one 0x1038 |

PowerShell is left unfiltered on purpose, since Out-Minidump is PowerShell.
The Azure path is left out because environment-specific filters belong in a
deployment rather than in a published rule, and filtering them here would make
the number look better than the rule is.

One of the 8 deserves naming. `empire_over_pth_patch_lsass` is labelled
T1550.002, so it is legitimately in the benign corpus for T1003.001, and Empire's
over-pass-the-hash does patch LSASS memory. Counting it as a false positive is
the strict reading and that is how it is counted.

This is one rule measured on one corpus. It has not been run anywhere near a
production estate, and the false positive rate on a real fleet with real
software will be higher.

## The rest of the chain

The other five rules cover stages that appear in the same captures. Coverage is
uneven, and the table says so rather than filling in. Full numbers are in
`benchmark/chain.md`.

| rule | technique | detects | fp/100k | benign events |
|---|---|---|---|---|
| Process Started From A User Download Directory | T1204.002 | 7/7 | 0.99 | 608,813 |
| LSASS Handle Request From Unexpected Process | T1003.001 | 7/7 | 1.56 | 514,202 |
| SeDebugPrivilege Enabled On A Token | T1134.001 | 4/7 | 1.48 | 608,813 |
| Remote Thread Started From Unbacked Memory | T1055.002 | 3/7 | 1.02 | 589,112 |
| LSASS Dump Via Comsvcs MiniDump Export | T1003.001 | 1/7 | 0.00 | 514,202 |
| PowerShell Script Block Calling MiniDumpWriteDump | T1003.001 | 1/7 | 0.00 | 514,202 |

The low counts are not failures. Only three of the seven intrusions inject into
another process, only one goes through comsvcs, and only one uses PowerShell to
call MiniDumpWriteDump. Each rule fires on the captures that contain the thing
it looks for. A rule detecting 1 of 7 here is a rule with one capture to detect,
which is a statement about the corpus.

The SeDebugPrivilege rule is the weak one. It fires on 4 of 7 and costs 1.48 per
100k on its own, and it says nothing by itself: enabling a privilege is not
using it. It earns its place next to the LSASS handle rule and not on its own.

## Against an intrusion none of them was written for

The whole set was pointed at the APT29 ATT&CK evaluation captures, 783,367
events across two days and several hosts.

| capture | events | fired |
|---|---|---|
| day 1 | 196,081 | LSASS handle (2), unbacked remote thread (2), SeDebugPrivilege (1) |
| day 2 | 587,286 | LSASS handle (2), unbacked remote thread (2), SeDebugPrivilege (2) |

Three of the six fire, on hosts and tooling the rules were not tuned against.
The three that stay quiet are the narrow ones: comsvcs, the PowerShell dump
script, and the download-directory rule, none of which describes how this
intrusion moved.

This is the closest thing here to a test of whether the LSASS rule generalises
past the corpus it was built on. Two matches per day on different hosts, with
no tuning, is a reasonable sign that it keys on something real. It is one more
dataset, not a deployment.

## Cross-check

The evaluator here is mine, so before publishing any of these misses the same
rules and captures were run through
[Zircolite](https://github.com/wagga40/Zircolite), which converts Sigma to SQL
and shares no matching code with this. Seven campaigns, 23 `process_access`
rules: the two agree on which rules fire and on how many events each matches,
with no disagreements. `python -m eval.crosscheck` reruns it and
`benchmark/crosscheck.json` holds the output.

The comparison covers the `process_access` rule set, not all 81 selected rules.

## Limitations

Seven tools is seven tools. One lab, one Sysmon configuration, one operator's
habits about where to drop a binary and what to call it. A field missing from a
capture is not proof it would be missing in production, which is why telemetry
gaps are separated from logic misses instead of counted against the rules.

The benign corpus is 91 atomic attack simulations, real host telemetry but a
quiet one. 514,202 events separates a rule that fires a handful of times from
one that fires constantly. It does not support comparing 0.1 against 0.3 per
100k, and no such comparison is drawn here.

None of this is a verdict on SigmaHQ. Their rules are written for far more
environments than these seven captures, and a rule that misses here may be
carrying its weight somewhere this corpus cannot see.

## Reproducing

```bash
pip install -r requirements.txt pyyaml
python -m eval.corpus --fetch     # about 1.5 GB, pinned and checksummed
python -m eval.report --run       # writes benchmark/results.json and results.md
python -m eval.report --check     # fails if committed results drift
```
