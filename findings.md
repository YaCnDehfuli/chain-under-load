# Findings

What 81 Sigma rules for LSASS credential dumping do when they meet seven real
dumping tools, and what the misses have in common.

Every number here comes from `benchmark/results.json`,
`benchmark/selection.json`, `benchmark/sensitivity.json` or
`benchmark/robustness.json`, regenerated by `python -m eval.report --run` and
`--run-selection`. Method is in [docs/method.md](docs/method.md).

## What was measured

Seven captures from OTRF/Security-Datasets, each one recording of the same
technique carried out with a different tool, on the same lab host with the same
Sysmon configuration. 354,229 events in total.

| tool | events | what it is |
|---|---|---|
| logonpasswords | 53,698 | mimikatz-style in-process read |
| procdump | 42,482 | signed Sysinternals binary |
| comsvcs | 41,954 | rundll32 calling the comsvcs MiniDump export |
| out-minidump | 40,568 | PowerShell reflective MiniDumpWriteDump |
| sharpdump | 59,707 | .NET port of out-minidump |
| outflank-dumpert | 58,096 | direct syscalls, avoids userland hooks |
| nanodump | 57,724 | syscalls plus a hand-rolled minidump writer |

80 published rules select for T1003.001, 79 by ATT&CK tag and 1 by logsource.
Three rules from this repo carry the same tag, making 83 in the run. No rule
failed to compile.

## Coverage per tool

| tool | published rules firing | including this repo |
|---|---|---|
| out-minidump | 8 | 10 |
| procdump | 7 | 8 |
| comsvcs | 6 | 8 |
| outflank-dumpert | 5 | 6 |
| logonpasswords | 3 | 4 |
| sharpdump | 3 | 4 |
| nanodump | 3 | 4 |

Each tool trips between 3 and 8 published rules, median 5. 18 of the 80 fire on
at least one tool. The other 62 target tooling this corpus does not contain,
which is why the report leans on per-tool coverage rather than a per-rule score.
Of the 581 rule and capture pairs, 44 detected, 207 were logic misses, 273 out
of scope, and 57 were telemetry gaps.

No published rule detects more than 4 of the 7.

## The misses have a shape

### All three nanodump detections are one string

nanodump's three published detections each key on the literal `dump` appearing
somewhere the operator chose:

| rule | what it matched |
|---|---|
| LSASS Memory Access by Tool With Dump Keyword In Name | `SourceImage` was `nanodump.x64.exe` |
| LSASS Process Memory Dump Files | `TargetFilename` was `lsass_dump.dmp` |
| LSASS Dump Keyword In CommandLine | the same filename on the command line |

Rename the binary and the output file and all three stop firing, which takes
nanodump's published coverage to zero. sharpdump is in a similar position, with
two of its three published detections needing `dump` in the image name.

The behaviour underneath is still there. nanodump opened LSASS with
`GrantedAccess` `0x1010`, and `0x1010` is commented out of the two main
access-mask rules:

```yaml
# from proc_access_win_lsass_memdump.yml
GrantedAccess|contains:
    - '0x1038'
    - '0x1438'
    - '0x143a'
    - '0x1fffff' # Too many false positives
    # - '0x01000'  # Too many false positives
    # - '0x1010'   # Too many false positives
    # - '0x1400'  # Too many false positives
    # - '0x1410' # Too many false positives
```

That is a deliberate trade by the rule authors, not an oversight. It is worth
knowing that the trade costs nanodump and the in-process mimikatz read, both of
which use the masks that were removed.

### A directory filter that the tools walk straight through

`Potentially Suspicious GrantedAccess Flags On LSASS` drops every event whose
source lives in an ordinary program directory:

```yaml
filter_main_generic:
    SourceImage|contains:
        - ':\Program Files (x86)\'
        - ':\Program Files\'
        - ':\Windows\System32\'
        - ':\Windows\SysWOW64\'
```

In these captures procdump ran from `C:\Program Files\procdump64.exe`, SharpDump
from `C:\Program Files\SharpDump.exe`, and nanodump from
`C:\Windows\System32\nanodump.x64.exe`. The filter is there to suppress the
system processes that read LSASS constantly, and it does that. It also means
writing to a directory an operator can usually write to is enough to leave the
rule's field of view.

### Where the telemetry ran out

57 of the misses are the capture, not the rule. Most are rules reading a
channel this Sysmon configuration did not record, and they are reported
separately for that reason.

One of these bit me while writing my own rules. These captures carry process
creation on both Sysmon EventID 1 and Security 4688, but the flattened 4688
events expose the command line as `CommandLine`, not the `ProcessCommandLine`
that a 4688 rule would normally name. My first comsvcs rule used the documented
field, detected 0 of 7, and looked like a logic problem until the field
inventory said otherwise. Rewritten against `process_creation`, it detects the
capture it was written for. That is the exact failure mode `miss-telemetry`
exists to catch, and it is a good argument for classifying misses rather than
counting them.

## My rule

`rules/t1003_001_lsass_handle.yml` detects 7 of 7, with 8 false positives in
514,202 benign events, a rate of 1.56 per 100k.

It keys on the caller rather than on names the operator picks. Filters pin a
binary to its expected directory instead of excluding directories wholesale,
which is the gap nanodump used by running from System32 under its own name.

The 8 false positives, in full:

| source | count | note |
|---|---|---|
| Azure `CollectGuestLogs.exe` | 6 | guest agent, six build-specific paths |
| `powershell.exe` | 2 | one 0x1010, one 0x1038 |

PowerShell is left unfiltered on purpose, since Out-Minidump is PowerShell.
The Azure path is left out because environment-specific filters belong in a
deployment rather than in a published rule, and filtering them here would make
the number look better than the rule is.

One of the 8 deserves naming. `empire_over_pth_patch_lsass` is labelled
T1550.002, so it is legitimately in the benign corpus for T1003.001, and Empire's
over-pass-the-hash does patch LSASS memory. Counting it as a false positive is
the strict reading and that is how it is counted. It is also why
[docs/method.md](docs/method.md) now calls this quantity a non-target fire rate
rather than a false-positive rate, and separates both from the two rates this
corpus cannot produce.

This is one rule measured on one corpus. It has not been run anywhere near a
production estate, and the rate on a real fleet with real software will be
higher.

## What a rename costs

Everything above measures the tools as their operators happened to name them.
That is an upper bound. Each capture was replayed through five tiers of adversary
effort, each a superset of the one below. Method and the restrictions on what may
be rewritten are in [docs/method.md](docs/method.md); every number here comes from
`benchmark/sensitivity.json`.

A rule counts in this table when it matches any event in the capture, which is
the measure `benchmark/results.json` uses, so this table and the coverage table
above can be read together.

| tool | T0 | T1 rename | T2 relocate | T3 strip-pe | T4 new identity | intrusion-linked events |
|---|---|---|---|---|---|---|
| out-minidump | 8 | 7 | 4 | 4 | 4 | 579 of 40,568 |
| procdump | 7 | 3 | 3 | 3 | 3 | 524 of 42,482 |
| comsvcs | 6 | 5 | 4 | 4 | 4 | 903 of 41,954 |
| outflank-dumpert | 5 | 3 | 1 | 1 | 1 | 468 of 58,096 |
| logonpasswords | 3 | 3 | 1 | 1 | 1 | 1,009 of 53,698 |
| sharpdump | 3 | 2 | 2 | 2 | 2 | 489 of 59,707 |
| nanodump | 3 | 0 | 0 | 0 | 0 | 470 of 57,724 |

Renaming what the operator brought is the cheapest thing available, and it
removes 12 of the 35 published detections across the seven tools. Moving those
artifacts into a directory the mask rules exclude removes 8 more, leaving 15 of
35. The median tool goes from 5 detections to 3 to 2.

**nanodump goes to zero at the rename.** Phase 1 argued from the rule text that
all three of its detections keyed on the string `dump`, in the image name, in the
output filename, and in the command line carrying that filename. All three go,
and nothing in the technique-scoped selection replaces them. The behaviour is
unchanged: it still opens LSASS with `0x1010` and still writes a minidump.

**procdump loses four of seven at the rename**: `Procdump Execution`, `Cred Dump
Tools Dropped Files`, `LSASS Memory Access by Tool With Dump Keyword In Name` and
`LSASS Process Memory Dump Files`. The three that survive are worth naming,
because none of them reads the name of the file on disk. `Potential Credential
Dumping Activity Via LSASS` reads the access mask and the call trace. `LSASS Dump
Keyword In CommandLine` reads `lsass` and `.dmp` in the command line, and the
operator renamed the binary and the output file but still had to name the victim
process. `Potential LSASS Process Dump Via Procdump` is named after the tool and
does not read its name at all: it requires `-ma` and a string like ` ls` in the
command line, so it catches ProcDump's flags rather than ProcDump's filename.
That is the shape a rename-resistant rule has, arrived at without anyone
advertising it.

**Relocation costs the mask rules, which read no filename at all.** T2 is where
`Uncommon GrantedAccess Flags On LSASS`, `Potentially Suspicious AccessMask
Requested From LSASS`, `Potentially Suspicious GrantedAccess Flags On LSASS`,
`LSASS Access From Non System Account`, `LSASS Access From Program In Potentially
Suspicious Folder` and `Suspicious Process Access to LSASS with Dbgcore/Dbghelp
DLLs` drop out, on whichever tools they were catching. They are lost to their own
filters: the ones excluding every `SourceImage` under `Program Files`, `System32`
and `SysWOW64`, which Phase 1 flagged from reading the rule text and this
measures. Moving a renamed binary one directory is one command, and it removes
the behavioural detections that survived the rename.

logonpasswords shows that on its own. It reads LSASS from a thread injected by
the payload, so nothing it does is name-dependent and the rename costs it
nothing. Relocating the payload out of `\Downloads\` costs it two of three.

**T3 and T4 move nothing in this population.** Clearing the version resource and
rotating the fingerprints change no outcome for any of the seven tools. That is
not because those tiers do nothing. It is because the layer that reads a version
resource or a fingerprint to catch a renamed tool is not in the population being
measured, which is what the next section is about.

### Crediting only the events the intrusion named

A capture is a full recording window and between one and two percent of it is the
intrusion. Counting a rule as covering a tool because it fired somewhere in that
window credits background activity, so there is a second, stricter reading:
a rule is credited only when it matches an event naming an artifact the operator
brought or wrote.

| tool | T0 | T1 | T2 | T3 | T4 |
|---|---|---|---|---|---|
| out-minidump | 8 | 7 | 3 | 3 | 3 |
| procdump | 7 | 3 | 3 | 3 | 3 |
| comsvcs | 5 | 4 | 2 | 2 | 2 |
| outflank-dumpert | 5 | 3 | 1 | 1 | 1 |
| logonpasswords | 3 | 3 | 1 | 1 | 1 |
| sharpdump | 3 | 2 | 2 | 2 | 2 |
| nanodump | 3 | 0 | 0 | 0 | 0 |

The two readings agree on five of the seven tools, and where they disagree the
disagreement is worth reading rather than averaging.

`Lsass Memory Dump via Comsvcs DLL` fires on the comsvcs capture at every tier
and is credited at none of them. It is right about the intrusion and the crediting
rule cannot see that, because the event it matches is `rundll32.exe` loading
`comsvcs.dll`, and both of those are Windows files the operator did not bring and
cannot rename. Intrusion linkage is defined by what a rename touches, so a lolbin
technique is exactly the case it under-credits: the whole point of a lolbin is
that nothing about it is the operator's to name. That is a limitation of the
measure, stated here rather than hidden by picking whichever number is larger.

`Potentially Suspicious AccessMask Requested From LSASS` is the other one. It
stops being credited on comsvcs and out-minidump at the relocation, and keeps
firing on background LSASS access in the same captures. Counting that as coverage
would be counting a Windows service reading LSASS as a detection of the dump.

The gap matters far more in the wide population below, where most of what fires
is background: 38 rules match something in the logonpasswords capture and 10
match an event the intrusion named.

### The control

The reason to believe any of the above. Beside the ladder, and not a rung of it,
one mutation rewrites `CurrentDirectory` and nothing else. No rule in the
selection requires that field, which a test asserts against the pinned rule tree
rather than taking on trust.

It moves nothing, on all seven captures, on both readings, in `S-tag`, `S-aug`
and the rules from this repository: no rule loses a credit, gains one, stops
firing or starts. A mutator damaging events would show up there first.

It does move something in the wide population, and that is the other half of the
argument. `LOLBIN Execution From Abnormal Drive` filters on
`CurrentDirectory|contains: 'C:\'`, so rewriting the drive letter removes its
filter and the rule starts firing on five of the seven captures. A control no
rule could see would pass by construction and would demonstrate nothing. This one
is visible to a rule that reads the field it rewrites, that rule moves, and this
harness reports it.

### The tiers are a model, and the rules in this repo are not evidence about published ones

There is no capture of these seven tools run under different names, so the tiers
are substitutions applied to the recording rather than seven more intrusions. The
restrictions on what may be substituted are in
[docs/method.md](docs/method.md), and they are the reason a loss can be attributed
to the change that caused it. Every one of them makes the measured loss smaller
than it would otherwise look.

Three of the rules in `rules/` carry `attack.t1003.001` and are run in the same
pass, reported as their own population and excluded from every number above. They
are unmoved by every tier on every tool: 1 credited on five of the seven captures
and 2 on comsvcs and out-minidump, at T0 and at T4 alike.

That is a feasibility demonstration and not a control. Those rules were written
after reading the Phase 1 results, against the gaps those results found, so their
durability here is close to circular. What it does establish is a lower bound on
what this telemetry supports, which bounds how much of the published fragility is
inherent to the recording rather than to the rules.

One caveat on the same rules, in the other direction: `Process Started From A
User Download Directory` is a T1204.002 rule and so is not in this population,
which means the tier that would defeat it, the relocation out of `\Downloads\`,
is not applied to it here. `docs/deploying.md` names that as its known blind
spot.

### Renaming procdump makes coverage go up, if you are looking wide enough

The tag-scoped selection takes procdump from 7 rules to 3 at the rename. The wide
population takes it from 14 to 13, because three rules *arrive* at T1 that were
silent at T0:

- `Renamed ProcDump Execution`, which reads `OriginalFileName: 'procdump'` and
  then suppresses itself with `filter_main_known_names` on `Image|endswith`
  `\procdump.exe`. Both procdump images in the capture record that
  `OriginalFileName` exactly and both match that filter, so at T0 the rule
  silences itself and at T1 the rename removes the filter. Measured directly: 0
  matches at T0, 2 at T1, and still 2 at T3 and T4.
- `Suspicious Execution Of Renamed Sysinternals Tools - Registry` and `Usage of
  Renamed Sysinternals Tools - RegistrySet`, which read the
  `SOFTWARE\Sysinternals\ProcDump` key that ProcDump writes under its own name
  whatever the file is called. No tier here rewrites that key, which is why they
  work and why the mutator is careful not to touch it.

None of the three carries `attack.t1003.001`. The first is tagged
`attack.t1036.003`, which is correct: it fires on `selection_ofn` alone, with no
LSASS target and no dump-specific command line, so it detects any renamed
procdump regardless of what it was used for. It is a masquerading rule and it
should be tagged as one. The problem is not the tag. It is that nothing connects
the two layers, so a reader assembling T1003.001 coverage has no way to find out
that the rename case is already handled somewhere else.
[contrib/coverage-mapping-issue.md](contrib/coverage-mapping-issue.md) is the
draft that says so.

### One tool keeps a fingerprint-keyed rule until the fingerprint changes

outflank-dumpert is the only tool where T4 costs anything at all: the wide
population goes from 9 to 8. The rule lost is `Hacktool Execution - Imphash`,
which carries the tool's import hash, and the diagnostic run says which half of
the fingerprint it read. Rotating the crypto digests alone leaves it firing;
rotating the import profile alone removes it. That is the pre-registered
durability hypothesis holding for the one rule in this corpus it applies to.

It is also the one place where the same value appears twice in SigmaHQ, spelled
two ways. `HackTool - Dumpert Process Dumper Execution` carries
`Hashes|contains: 'MD5=09D278F9DE118EF09163C6140255C690'`; that value is the
build's import hash, its MD5 is something else, and the rule therefore matches
nothing on the tool it is named after. Measured: 0 matches as committed, 1 with
`IMPHASH=`. It is tagged `attack.t1003.001` and the rule that does fire is not.
[contrib/dumpert-imphash-correction.md](contrib/dumpert-imphash-correction.md).

### For nanodump nothing in the wide population is about credential access

Widening the population does not rescue nanodump. It goes 3 to 0 in both scoped
populations at the rename, and the 9 rules `W` still credits at T1 are about the
delivery rather than the dump: an executable written into an alternate data
stream, a download from a bare IP address, a new entry in the AppCompat store.
The build in this corpus has imphash `DD21BA5E5A241C35E3FC3EC6E6F33920`, and
neither it nor the build's MD5, SHA1 or SHA256 occurs anywhere in the pinned
tree, even though `Hacktool Execution - Imphash` carries 15 other NanoDump
imphashes. Nothing in 3,747 published rules identifies this build once it is
renamed.

### What intrusion linkage does and does not establish

An event counts as intrusion-linked when the rename substitution changes it, which
is mechanical and needs no hand-labelling. All seven intrusions were delivered by
the same metasploit payload, and renaming it is renaming a file the operator named
as freely as anything else, so the linked set is every event that names something
the operator put on the host.

| capture | events | intrusion-linked | share | rules offered | admitted by the prescreen |
|---|---|---|---|---|---|
| logonpasswords | 53,698 | 1,009 | 1.88% | 2,604 | 623 |
| procdump | 42,482 | 524 | 1.23% | 2,604 | 535 |
| comsvcs | 41,954 | 903 | 2.15% | 2,604 | 609 |
| out-minidump | 40,568 | 579 | 1.43% | 2,604 | 571 |
| sharpdump | 59,707 | 489 | 0.82% | 2,604 | 513 |
| outflank-dumpert | 58,096 | 468 | 0.81% | 2,604 | 480 |
| nanodump | 57,724 | 470 | 0.81% | 2,604 | 488 |

The difference the crediting rule makes is large in the wide population and small
in the scoped one. On out-minidump, 37 rules in `W` match something at T0 and 27
match an intrusion-linked event; on logonpasswords it is 38 and 10. Counting the
first number as coverage would have reported the background of a lab recording as
a compensating detection layer.

That is a necessary condition for detecting the intrusion, not a sufficient one
for detecting the credential dump. A rule credited on an event naming the delivery
payload saw the intrusion; whether it saw the dump is a separate question the
harness cannot answer. This is why the compensating layer is reported rule by rule
in `benchmark/selection.md` rather than as a count, and why the counts above are
not a claim that the wide population catches credential dumping.

## The robustness record, and where the hypothesis was wrong

`benchmark/robustness.md` records six things per rule, unweighted and
uncombined: which tools it is credited on, which tiers it survives, what it
requires from the telemetry, which provenance class those requirements fall in,
its non-target fire rate, and its clean-baseline rate, which is unmeasured and
labelled so rather than shown as zero. 83 rules match something at the baseline
and, grouped by measured overlap of their intrusion-linked match sets, the ones
credited with coverage are 39 effective families. Eighty rules is not eighty
detections.

The pre-registered hypothesis was that durability follows what a rule keys on:
fingerprint-keyed survives the rename and fails at T4, mask-keyed survives the
rename and fails on directory exclusion, name-keyed fails at T1. Measured against
51 credited rules, that ordering is right about the direction and wrong as a
prediction, in two different ways.

**35 rules were lost at a tier other than the first one that rewrites a field
they require.** 34 of them survived longer than the class suggests, because the
class says which tier can reach a field and not whether the substitution
applied to that field defeats the rule. A rule requiring `Image` is
runtime-controlled, but if the `Image` it wants is `\powershell.exe` then
renaming what the operator brought leaves it matching. The class is a bound on
durability, not a forecast of loss, and the record now says so in that column's
name.

**One rule was lost earlier than any analysis of its requirements could
predict.** `Elevated System Shell Spawned From Uncommon Parent Location` reads a
version resource, which no tier below T3 touches, and it stops being credited at
T2. The relocation moved the payload into `C:\Program Files`, and the rule's
filter treats that as a common parent location. `required_groups` walks only the
AND spine, so a detection removed by a filter that starts applying is invisible
to it. Three of the mask rules are lost the same way and are correctly predicted
only by accident.

That is the substance of the ordering: what a rule requires bounds when it can be
lost; what a rule excludes decides when it is. Filters are half the durability
story and the half that no static reading of the selection captures.

The low counts are not failures. Only three of the seven intrusions inject into

The SeDebugPrivilege rule is the weak one. It fires on 4 of 7 and costs 1.48 per
100k on its own, and it says nothing by itself: enabling a privilege is not
using it. It earns its place next to the LSASS handle rule and not on its own.

## Transferred to an intrusion none of them was written for

The whole set was pointed at the APT29 ATT&CK evaluation captures, 783,367
events across two days and several hosts. This is a transfer test rather than a
reconstruction: nothing here anchors a step of that intrusion to the events it
produced, and `docs/decisions.md` says why the module doing it is no longer
called a chain.

| capture | events | fired |
|---|---|---|
| day 1 | 196,081 | LSASS handle (2), unbacked remote thread (2), SeDebugPrivilege (1) |
| day 2 | 587,286 | LSASS handle (2), unbacked remote thread (2), SeDebugPrivilege (2) |

Three of the six fire, on hosts and tooling the rules were not tuned against.
The three that stay quiet are the narrow ones: comsvcs, the PowerShell dump
script, and the download-directory rule, none of which describes how this
intrusion moved.

This is the closest thing here to a test of whether the LSASS rule generalises
past the corpus it was built on. Two matches per day on different hosts, with
no tuning, is a reasonable sign that it keys on something real. It is one more
dataset, not a deployment.

## Cross-check

The evaluator here is mine, so before publishing any of these misses the same
rules and captures were run through
[Zircolite](https://github.com/wagga40/Zircolite), which converts Sigma to SQL
and shares no matching code with this. Seven campaigns, 23 `process_access`
rules: the two agree on which rules fire and on how many events each matches,
with no disagreements. `python -m eval.crosscheck` reruns it and
`benchmark/crosscheck.json` holds the output.

The comparison covers the `process_access` rule set, not all 81 selected rules.

## Limitations

Seven tools is seven tools. One lab, one Sysmon configuration, one operator's
habits about where to drop a binary and what to call it. A field missing from a
capture is not proof it would be missing in production, which is why telemetry
gaps are separated from logic misses instead of counted against the rules.

The benign corpus is 91 atomic attack simulations, real host telemetry but a
quiet one. 514,202 events separates a rule that fires a handful of times from
one that fires constantly. It does not support comparing 0.1 against 0.3 per
100k, and no such comparison is drawn here.

None of this is a verdict on SigmaHQ. Their rules are written for far more
environments than these seven captures, and a rule that misses here may be
carrying its weight somewhere this corpus cannot see.
